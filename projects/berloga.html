Berloga: Destroy(evil)

Сюжетная 2.5D-головоломка. Машинами не управляешь напрямую: ты задаёшь им последовательность команд и смотришь, решает ли она комнату. A story-driven 2.5D puzzle game. You do not control the machines directly: you give them a sequence of commands and watch whether the sequence solves the room.

ЗадачаThe problem

Игра делалась под олимпиаду НТО с жёстким дедлайном и в команде. Уровни надо было собирать быстро и много, а сюжет и головоломки писались параллельно с кодом. Значит, движок игры должен был позволять придумать новую комнату без единой строчки нового кода. The game was built for the NTO olympiad against a hard deadline, in a team. Levels had to be authored quickly and in quantity, while the story and the puzzles were being written alongside the code. So the game had to let us invent a new room without writing new code.

Что делал яWhat I did

Я был программистом и тимлидом: весь код игры и координация команды из четырёх человек — Артемий Приоров (документация и звук), Григорий Ларкин (2D-графика и тестирование), Полина Внукова (3D-модели и текстуры). I was the programmer and the team lead: all of the game code, plus coordinating a team of four — Artemiy Priorov (documentation and audio), Grigory Larkin (2D art and testing), Polina Vnukova (3D models and textures).

Техническое решениеHow it works

Всё, что умеет машина, — это объект-команда. Есть базовый Action и около двух десятков конкретных: проехать вперёд, повернуть, включить двигатель, открыть портал, повернуть зеркало по X или по Y, вспахать поле, засеять, полить, удобрить. Головоломки собираются композицией этих команд, а не отдельной логикой под каждый уровень — именно поэтому уровни удалось быстро дописывать у дедлайна. Everything a machine can do is a command object. There is a base Action and about two dozen concrete ones: move forward, rotate, start the engine, open a portal, rotate a mirror around X or Y, plough a field, sow it, water it, fertilise it. Puzzles are built by composing these rather than by writing per-puzzle logic — which is exactly why the levels could be authored quickly near the deadline.

У каждого интерактивного объекта своя машина состояний. CarStates, CraneStates и парные к ним файлы действий держат правила объекта рядом с самим объектом, а не в одном центральном контроллере. Крану не нужно знать, что такое машина. Each interactable object has its own state machine. CarStates, CraneStates and their matching action files keep an object's rules next to the object instead of in one central controller. A crane does not need to know what a car is.

Поверх этого — система диалогов с триггерами для сюжетных сцен и система артефактов и алтарей, которая гейтит продвижение по игре. On top of that there is a dialogue system with triggers for the story sections, and an artefact and altar system that gates progress.

Что бы я сделал иначе сегодняWhat I would do differently today

Команды стали бы данными, а не классами. Из двадцати трёх наследников Action около пятнадцати отличаются только тем, какое значение они кладут. Сегодня я сделал бы один тип действия, настраиваемый через ScriptableObject, чтобы геймдизайнер мог добавить машине новый глагол без программиста. Actions would be data, not classes. Of the twenty-three Action subclasses, about fifteen differ only in which value they push. Today I would make one action type configured by a ScriptableObject, so a designer could add a machine verb without a programmer.
